# .NET / C# reference for audit-infra-and-deployment

## Stack markers
- `*.csproj` with `Sdk="Microsoft.NET.Sdk.Web"` (ASP.NET Core) or `Microsoft.NET.Sdk.Worker` (background worker).
- `Dockerfile` generated by Visual Studio (`FROM mcr.microsoft.com/dotnet/aspnet:8.0 AS base` ... `AS build` ... `AS publish` ... `AS final`).
- SDK container builds with **no Dockerfile**: `<ContainerBaseImage>`, `<ContainerRepository>`, `<ContainerUser>` in the csproj and `dotnet publish /t:PublishContainer`. No Dockerfile does not mean no image, so check for these properties.
- .NET Aspire (`*.AppHost.csproj`, `Aspire.Hosting`), `azure.yaml` (azd), `*.pubxml` (Web Deploy / App Service), `web.config` (IIS), `docker-compose.dcproj` + `docker-compose.override.yml` (Visual Studio local only).
- Gateways: Ocelot (`ocelot*.json`) or YARP. Their downstream host names and ports must match the manifests.

## Where the relevant code lives
- `Dockerfile` beside each service csproj, or one at the solution root with `COPY ["Svc/Svc.csproj", "Svc/"]` lines. Then the build context is the solution root and the `.dockerignore` must be there too.
- `Program.cs`: `AddHealthChecks()` / `MapHealthChecks(...)`, `UseForwardedHeaders`, `UseHttpsRedirection`, `Database.Migrate()` at startup, `AddDataProtection()`.
- `appsettings.{Environment}.json` holds per-environment config (environment parity). `Properties/launchSettings.json` is dev-only.
- `.github/workflows`, `azure-pipelines.yml`: how images are tagged and how slots or rollouts are switched.

## Dangerous / interesting APIs and patterns
Base images and users:
- Final stage `FROM mcr.microsoft.com/dotnet/sdk:*` ships compilers, NuGet caches and source. The runtime stage should be `aspnet` (web), `runtime` (console/worker) or `runtime-deps` (self-contained / Native AOT).
- .NET 8+ images create a non-root `app` user and export `APP_UID=1654`, so use `USER $APP_UID` (or `USER app`). Chiseled images (`8.0-jammy-chiseled`, `9.0-noble-chiseled`, `-extra` variants for ICU/tzdata) are non-root by default and have no shell or package manager.
- The default listen port moved from 80 to **8080** in .NET 8 (`ASPNETCORE_HTTP_PORTS=8080`). An old `ENV ASPNETCORE_URLS=http://+:80` cannot bind as non-root, and that is often why a team switched back to `USER root`.
- `ENV ASPNETCORE_ENVIRONMENT=Development` baked into an image or manifest turns on the developer exception page and detailed errors in production.

Secrets:
- `ENV ConnectionStrings__Default=...Password=...`, `COPY appsettings.Production.json`, `COPY *.pfx` plus `ASPNETCORE_Kestrel__Certificates__Default__Password` all end up in image layers.
- `dotnet dev-certs https` inside a Dockerfile: a dev certificate is not a production TLS strategy.
- Good: `builder.Configuration.AddAzureKeyVault(...)`, a Kubernetes `secretKeyRef` mapped to `ConnectionStrings__Default`, `/run/secrets/*` read via `AddKeyPerFile("/run/secrets")`.

Runtime behaviour that affects deployment:
- No `MapHealthChecks` means probes have nothing meaningful to hit. Liveness and readiness should differ: tag database checks `"ready"` and map `/healthz/ready` with a predicate. Liveness should not depend on the database.
- TLS terminated at an ingress or load balancer but no `UseForwardedHeaders` with `ForwardedHeaders.XForwardedProto`: `UseHttpsRedirection` loops, or generated links use `http://`.
- `context.Database.Migrate()` in `Program.cs` with more than one replica gives concurrent migrations on rollout and no clean rollback path. Prefer a migration Job or pipeline step with `dotnet ef migrations bundle` or an idempotent script (`dotnet ef migrations script --idempotent`).
- Data Protection keys not persisted (`PersistKeysToDbContext`, `PersistKeysToAzureBlobStorage`): every redeploy or scale-out invalidates auth cookies and antiforgery tokens.
- Hangfire / `BackgroundService` jobs running in every replica duplicate work after scale-out. Check the server and queue configuration.
- Memory: .NET honours cgroup limits. Without a Kubernetes memory limit, the GC sizes the heap to the whole node. `DOTNET_GCHeapHardLimitPercent` tunes it.

## What "good" looks like
```dockerfile
# syntax=docker/dockerfile:1
FROM mcr.microsoft.com/dotnet/sdk:8.0@sha256:<digest> AS build
WORKDIR /src
COPY Api/Api.csproj Api/
RUN dotnet restore Api/Api.csproj
COPY . .
RUN dotnet publish Api/Api.csproj -c Release -o /app/publish --no-restore /p:UseAppHost=false

FROM mcr.microsoft.com/dotnet/aspnet:8.0-jammy-chiseled@sha256:<digest> AS final
WORKDIR /app
COPY --from=build /app/publish .
EXPOSE 8080
USER $APP_UID
ENTRYPOINT ["dotnet", "Api.dll"]
```
```csharp
builder.Services.AddHealthChecks()
    .AddDbContextCheck<AppDbContext>(tags: new[] { "ready" });
app.UseForwardedHeaders(new ForwardedHeadersOptions { ForwardedHeaders = ForwardedHeaders.XForwardedFor | ForwardedHeaders.XForwardedProto });
app.MapHealthChecks("/healthz/live", new() { Predicate = _ => false });
app.MapHealthChecks("/healthz/ready", new() { Predicate = c => c.Tags.Contains("ready") });
```
Chiseled images have no `curl`/`wget`, so rely on orchestrator probes instead of a Dockerfile `HEALTHCHECK`.

## Manual trace checklist
1. For each deployable service, find which Dockerfile or `PublishContainer` config builds it and which manifest or slot runs it. A service with neither is deployed by hand; record it.
2. Check the final stage base image, user and port. Compare `EXPOSE`/`ASPNETCORE_HTTP_PORTS` with the manifest `containerPort` and probe ports.
3. For every `ConnectionStrings__*`, `Jwt__*` and API key, find where the running container gets it (secret manager, `secretKeyRef`, App Service Key Vault reference).
4. Health endpoints exist and the probes point at them. Readiness depends on dependencies; liveness does not.
5. Migrations: who runs them, whether exactly once, and whether before or after the new version starts. Is there a down path for the last release?
6. Rollback: App Service slot swap back (`az webapp deployment slot swap --slot staging --target-slot production`), `kubectl rollout undo`, or the previous image tag. Check that the schema still works with the previous build.
7. Backups: Azure SQL PITR/LTR (`az sql db ltr-policy show`), SQL Server `BACKUP DATABASE ... TO URL` jobs, `sqlpackage /Action:Export`. Record the date of the last restore test.

## Stack-specific false positives
- `FROM mcr.microsoft.com/dotnet/sdk` in a stage that is not the last one is normal.
- No `USER` line with a `-chiseled` base, or `<ContainerUser>` unset on .NET 8+ SDK container builds (it defaults to `app`).
- `ASPNETCORE_ENVIRONMENT=Development` in `docker-compose.override.yml` or `launchSettings.json` is for Visual Studio local debugging only.
- `ARG BUILD_CONFIGURATION=Release` is not a secret, even though it is a build arg.

## Tooling
- `dotnet publish -c Release /t:PublishContainer -p ContainerImageTag=1.2.3`, then inspect the resulting user with `docker inspect --format '{{.Config.User}}' img`.
- `hadolint Dockerfile`, `trivy config .`, `checkov -d .` (see `tool-candidates.md`).
- `az webapp config show -g <rg> -n <app> --query "{https:httpsOnly,tls:minTlsVersion,alwaysOn:alwaysOn}"`, `az webapp deployment slot list`.
- `az sql db show --query "{pitr:earliestRestoreDate}"`, `az sql db ltr-backup list`.
- `dotnet ef migrations script <from> <to> --idempotent` to review the rollback script.
