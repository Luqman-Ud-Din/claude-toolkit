# Async and DI hazard classes

Pattern ids in `scripts/patterns/*.json` start with one of these codes; `di_lifetimes.py` emits the DI rows.

| Code | Class | Proof of defect | Proof of safety | Severity guidance |
|---|---|---|---|---|
| BLOCK | Synchronous wait on asynchronous work | `.Result`, `.Wait()`, `.GetAwaiter().GetResult()`, `Task.Run(...).Result`, `.block()`, `.get()`/`.join()` on futures, `deasync`, `asyncio.run` inside a running loop, `loop.run_until_complete` in a handler - on a request path, in a constructor, inside a lock, or in a library called from one | The awaited work is already complete (`Task.FromResult`, `ValueTask` with `IsCompleted`), the call is in a console entry point / test / startup, or the platform is documented as having no sync context *and* the path is cold | High on request paths and locks; Critical on WebFlux event loop / UI thread / legacy ASP.NET (deadlock); Low in startup code |
| VOID | Handler that cannot report errors | `async void` methods (not event handlers), Java `@Async void` without `AsyncUncaughtExceptionHandler`, JS `async` function called without `await`/`.catch` inside a route/handler/`setInterval`, Python `asyncio.create_task` result dropped, `async def` view called synchronously | Returns `Task`/`CompletableFuture`/`Promise` that the caller awaits; exceptions logged in a continuation; Nest/Express async wrapper (`express-async-errors`, Express 5) present | High when the handler performs writes or money movement; Medium otherwise |
| CANCEL | Cancellation not propagated | Controller/handler takes no `CancellationToken`/`AbortSignal`/`request.signal`; token accepted but not passed to `ToListAsync`, `SendAsync`, `Task.Delay`, `ReadAsync`; background loop ignores `stoppingToken`; `CancellationToken.None` / `default` passed explicitly | Token threaded from the action parameter to every awaited call; `stoppingToken` in `Task.Delay` and DB calls; `linkedTokenSource` with timeout | Medium for long queries/exports (work continues after the client left); Low otherwise; High for background loops that cannot stop (blocks shutdown) |
| FIRE | Fire-and-forget without error handling | `_ = SomethingAsync()`, `Task.Run(() => ...)` not awaited/tracked, `SomethingAsync();` (discarded Task), JS promise not awaited and no `.catch`, `threading.Thread(...).start()`, `@Async` without return, `CompletableFuture.runAsync` unobserved | Handed to a durable queue (Hangfire, BullMQ, Celery, Spring Batch); or tracked (`Task.WhenAll` later, `.catch(log)`, `add_done_callback`) and non-critical | High when the work is business-critical (invoice submission, stock update) - lost on crash; Medium otherwise |
| HTTP | HTTP client constructed per request | `new HttpClient()` in a method/handler/service constructor of a scoped/transient class; `new RestTemplate()`/`WebClient.create()`/`HttpClients.createDefault()` per call; `axios.create()` inside a handler; `requests.Session()`/`httpx.Client()` per call; `new PrismaClient()`/`new Pool()` per request (same class of bug) | `IHttpClientFactory` / typed client; single `RestTemplate`/`WebClient` bean; module-level axios instance / `http.Agent({ keepAlive })`; module-level `requests.Session`; one DB client per process | Medium (socket exhaustion, TIME_WAIT, DNS staleness); High on hot endpoints |
| TIMEOUT | Outbound call with no timeout | `HttpClient` default 100 s or `Timeout.InfiniteTimeSpan`; `RestTemplate` default (infinite); `WebClient` without `responseTimeout`; `axios` without `timeout`; `fetch` without `AbortSignal.timeout`; `requests.get` without `timeout=` (infinite); DB `CommandTimeout` 0 | Explicit timeout sized to the dependency SLA; resilience pipeline (Polly `AddStandardResilienceHandler`, Resilience4j `TimeLimiter`, `opossum`, `urllib3.Retry`+timeout) | Medium; High for calls on the main flow to third parties (payment, tax, SMS) |
| DI | Lifetime mismatch / container smells | Singleton (or hosted service) whose constructor takes a Scoped or disposable Transient; Spring singleton injecting `@RequestScope`/`prototype` bean without proxy/`ObjectProvider`; Nest singleton injecting `Scope.REQUEST` provider (bubbles - the singleton silently becomes per-request); `IServiceProvider` injected and used as a service locator; `BuildServiceProvider()` inside `ConfigureServices` (second container, duplicated singletons); `static` service instances; `new`ing a service that has DI dependencies | Consumer lifetime <= dependency lifetime; per-operation scope via `IServiceScopeFactory`/`ObjectProvider`/`ModuleRef.resolve`; `ValidateScopes`/`ValidateOnBuild` on | High for captive Scoped (DbContext, request context, tenant); Critical when multi-tenant; Medium for captive disposable Transient; Low for service-locator use |

## Lifetime ordering (for the DI table)
Singleton (process) > Scoped (request / job iteration) > Transient (per resolve). A consumer may hold only dependencies with lifetime >= its own. Nest: default singleton; `Scope.REQUEST` and `Scope.TRANSIENT` bubble up to injectors. Spring: default singleton; `prototype`, `request`, `session` need `proxyMode = TARGET_CLASS` or `ObjectProvider<T>` to be injected into singletons. Django: no container - see `python-django.md`.

## Rating notes
- "Works in dev" is not evidence: captive `DbContext` fails only when two requests overlap; `.Result` starves only when the pool is exhausted.
- Multiply by path heat: the same `.Result` on the login path is worse than on a nightly export.
- `confidence: likely` when the parser could not resolve a constructor parameter's registration (interface registered by assembly scanning, factory lambda).
