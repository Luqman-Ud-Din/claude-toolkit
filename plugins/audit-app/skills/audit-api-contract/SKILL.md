# Audit API contract

An API contract is a promise to every client, including the ones you do not
control. This skill checks that the promise is written down (spec), kept
(status codes, shapes, validation), safe (no entity leakage, no public spec in
production), and evolvable (versioning, breaking-change detection). It is
mostly mechanical: extract the endpoint table, then check each row.

Read-only rule: never modify the audited code. Write only under `audit/`.

## Inputs and prerequisites

- Path to the audited repository (backend; frontend root too, to see which endpoints and error shapes clients actually depend on).
- `audit/stack.json` if `audit-application` already ran; otherwise this skill runs `$AUDIT_CORE_ROOT/skills/audit-stack-detection/scripts/detect_stack.py`.
- Skills from the `audit-core` plugin (reached via `$AUDIT_CORE_ROOT`, exported by that plugin; a sibling `skills/` layout also works): `audit-stack-detection`, `audit-code-scan`, `audit-endpoint-inventory` (which itself needs `audit-sensitive-data-catalog`) and `audit-finding-writer`.
- Optional: the current OpenAPI file (`swagger.json`, `openapi.yaml`, generated by `swashbuckle`/`springdoc`/`swagger-jsdoc`/`drf-spectacular`) and a previous version of it (from git history, a release artifact, or the user). Without a spec the skill still audits the code; without a previous spec the breaking-change diff is skipped and listed under "Not checked".
- Python 3 for the bundled scripts; PyYAML only if the specs are YAML (JSON always works).

## Coordination with sibling skills

- `audit-authz-and-access-control` owns whether each endpoint is authorised; you own whether the spec/Swagger UI itself is reachable unauthenticated in production and whether responses leak fields. Both skills read the same endpoint inventory (`audit/evidence/audit-endpoint-inventory/endpoints.json`), so neither re-extracts.
- `audit-datetime-and-timezone` owns date correctness; you flag only the wire format (non-ISO 8601, missing offset) and hand the rest over.
- `audit-security-headers-and-middleware` owns CORS, content-type, and header hardening.
- `audit-injection-vulnerabilities` owns validation as a security control; you flag missing validation as a contract gap and cross-reference by `root_cause_key`.

## Workflow

1. **Resolve the stack.** Run `python "$AUDIT_CORE_ROOT/skills/audit-stack-detection/scripts/detect_stack.py" <repo>`. Open only the matching `references/<stack>.md` for the backend and, if present, the frontend. Always read `references/contract-checklist.md` (the nine contract properties, what evidence closes each, severity guidance). Unknown stack: `$AUDIT_CORE_ROOT/skills/audit-stack-detection/references/stack-reference-template.md`.
2. **Automated pass.**
   - Run `audit-endpoint-inventory` first, or reuse `audit/evidence/audit-endpoint-inventory/endpoints.json` when the orchestrator already produced it: `python "$AUDIT_CORE_ROOT/skills/audit-endpoint-inventory/scripts/inventory_endpoints.py" <repo>`. Build the endpoint table from its HTTP records (`kind == "http"`), or cite its `endpoints.md`: route `path_raw`, `method`, `handler`, versioned `versioned.status` yes/no, paginated `response.pagination.status` yes/no/n-a (collection reads without Skip/Take/limit markers are `no`), validated `validation.status` yes/no/n-a (validation markers in the handler or on the request type anywhere in the repo), response type `response.type`, exposed fields `response.sensitive_fields` (credential and secret names classified by `audit-sensitive-data-catalog` on the declared response type, e.g. `User.PasswordHash`), `response.returns_entity_like`, and error shape consistent `errors.consistent_with_majority` against `error_shapes.majority`. The summary lists come straight from those fields: `pagination.status == "no"` (unpaginated lists), `validation.status == "no"` (unvalidated bodies), non-empty `sensitive_fields` (exposed fields), and the files whose `consistent_with_majority` is `no` (outlier controllers).
   - `python "$AUDIT_CORE_ROOT/skills/audit-code-scan/scripts/grep_scan.py" <repo> --patterns scripts/patterns/<backend>.json [--patterns scripts/patterns/<frontend>.json] --out audit/evidence/audit-api-contract/hits.json --md audit/evidence/audit-api-contract/hits.md` finds spec exposure config, entities returned directly, sensitive fields on serialisable types, ad-hoc error objects, non-ISO date formats, and unversioned routes.
   - If two spec files exist: `python scripts/spec_diff.py <old> <new> --out audit/evidence/audit-api-contract/spec-diff.json --md audit/evidence/audit-api-contract/spec-diff.md` lists removed paths/operations, removed or newly-required request fields, changed types and enums, removed response fields, and changed status codes.
   Hits are pointers, not findings.
3. **Manual trace.** Complete the endpoint table by hand (the script cannot see through base classes, filters, or generic wrappers), then check in this order:
   1. **Spec exposure:** is Swagger UI / `/openapi.json` / `/v3/api-docs` / `/schema/` mounted in production config, and behind auth? Does the spec match the code (sample five endpoints)?
   2. **List endpoints:** every collection-returning route has page/size (or cursor), a maximum page size, and returns a total or next cursor.
   3. **Response DTOs:** for every endpoint returning an entity type or `SELECT *`, list the fields; flag secrets, hashes, internal flags, other-tenant ids, and navigation properties that drag in more entities. `response.sensitive_fields` covers credentials and secrets only, so internal flags, tenant keys and personal data still need this read (`python "$AUDIT_CORE_ROOT/skills/audit-sensitive-data-catalog/scripts/catalog.py" names <Field> ...` classifies a name). A token-issuing endpoint (login, refresh, token exchange) lists its token field there by design: that is expected, not an over-exposure finding.
   4. **Request DTOs:** every bound body has validation on required fields, ranges, lengths, enums, and rejects unknown fields where the stack supports it; unvalidated DTOs are findings.
   5. **Error shape and status codes:** collect every distinct error body shape across controllers; there should be one. Check 400 vs 422, 401 vs 403, 404 for missing/foreign resources, 409 for conflicts, 201 for creates, 204 for deletes, no 200-with-error-body.
   6. **Naming and dates:** casing consistent (camelCase JSON), plural nouns, no verbs in paths, ISO 8601 with offset for instants, `YYYY-MM-DD` for dates.
   7. **Versioning:** a strategy exists (path `/v1/`, header, or media type), is applied to every route, and breaking changes from the diff were versioned.
4. **Write findings** with `$AUDIT_CORE_ROOT/skills/audit-finding-writer/scripts/findings.py` (block below, prefix `API`). Rate with `audit-finding-writer/references/severity-rubric.md`: entity leakage of credentials or cross-tenant data is High/Critical; public spec in production is Medium (Low if the API is public by design); unpaginated lists Medium; inconsistent error shapes Low/Medium depending on client count; naming drift Info.
5. **Produce the outputs.**
   - `audit/findings/audit-api-contract.json` (`findings.py init` then `add`; `md` renders the findings section).
   - `audit/reports/audit-api-contract.md` in the template below: the endpoint table, error-shape inventory, spec diff (if any), findings, not checked.
   - `audit/evidence/audit-api-contract/` with `hits.json`, `spec-diff.json`, and any sampled responses the user captured. Endpoint facts stay in `audit/evidence/audit-endpoint-inventory/` and the report cites them.
   - `audit/status/audit-api-contract.json`: the status record defined in `audit-core:audit-finding-writer` (references/run-status.md).
6. **List what was not checked.** No previous spec (diff skipped), endpoints behind a gateway whose rewrite rules are outside the repo, generated clients, GraphQL/gRPC surfaces (out of scope for this skill), and anything handed to siblings. Put them in `scope.not_checked` and in the report.

## Finding format

Write findings using `audit-core:audit-finding-writer`, with ID prefix `API`.
Use its canonical schema and severity rubric. Topic-specific field guidance:

- **Location:** `path/to/file.ext:LINE` (symbol or route)
- **Evidence:**

```lang
<the handler, DTO, or config lines; or the spec-diff entry>
```

- **Impact:** Plain language: which clients break or what data leaks, how visible it is.
- **Remediation:** The concrete fix in this stack: DTO projection, pagination parameters with a cap, validation attributes/schema, one error envelope (RFC 9457), auth on the spec route, version segment.
- **Reference:** CWE-200 / CWE-213 (exposure), CWE-770 (unbounded), CWE-20 (validation), CWE-209 (error detail), ASVS-13.1.x / 13.2.x (API), ASVS-14.3.x (unintended info), OWASP-API3:2023 (property exposure), API4:2023 (unrestricted resource consumption), API8:2023 (misconfiguration), API9:2023 (inventory)

## Examples

**Input:** `UsersController.Get` returns `_db.Users.Find(id)` and `User` has `PasswordHash`, `SecurityStamp`, `CompanyId`.

**Output:**
```markdown
### [High] API-002 - GET /api/users/{id} returns the User entity including PasswordHash
- **Location:** `Users/UsersController.cs:27` (Get)
- **Confidence:** confirmed
- **Evidence:**

```csharp
[HttpGet("{id}")] public ActionResult<User> Get(int id) => _db.Users.Find(id);
// User: public string PasswordHash { get; set; } public string SecurityStamp { get; set; }
```

- **Impact:** Any caller who can read a user record also receives the password hash and security stamp, enabling offline cracking and token forgery; the fields also appear in logs and client caches. Rated High because it is reachable by ordinary authenticated users.
- **Remediation:** Return a `UserDto { Id, Email, DisplayName, RoleName }` projected with `.Select(u => new UserDto {...})` or an AutoMapper profile that never maps credential fields; mark the entity with `[JsonIgnore]` on `PasswordHash` as a second line of defence.
- **Reference:** CWE-200, ASVS-13.1.3, OWASP-API3:2023
```

**Input:** `ProductsController` returns `BadRequest(new { error = "..." })` while every other controller returns `ProblemDetails`.

**Output:** `[Low] API-003 - ProductsController uses an ad-hoc { error } body instead of ProblemDetails` with remediation to return `Problem(...)`/`ValidationProblem(...)` and let the global exception handler produce `application/problem+json`; reference ASVS-13.1.x, RFC 9457.

## Bundled files

- `references/contract-checklist.md` - the nine contract properties, evidence that closes each, status-code table, error-envelope guidance, severity guidance.
- `references/<stack>.md` - spec tooling, routing/versioning idioms, pagination and validation idioms, error handling, entity-leak shapes, false positives per stack (dotnet, java-spring, node-express, python-django, angular, react, vue); to add a stack, copy `$AUDIT_CORE_ROOT/skills/audit-stack-detection/references/stack-reference-template.md`.
