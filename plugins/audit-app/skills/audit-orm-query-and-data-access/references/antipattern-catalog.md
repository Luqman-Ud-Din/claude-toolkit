# Data-access anti-pattern catalog

Pattern ids in `scripts/patterns/*.json` start with one of these class codes.

| Code | Class | Proof of defect | Proof of safety | Severity guidance |
|---|---|---|---|---|
| NPLUS1 | Query inside a loop / lazy navigation in a loop | A `for`/`foreach`/`map`/`forEach` body calls the ORM (`First`, `Find`, `findOne`, `objects.get`, `getOne`) or touches a lazy navigation property (`order.Customer.Name` with lazy loading on, Hibernate `@ManyToOne` default EAGER on collections off) once per element | Collection loaded with parent (`Include`/`join fetch`/`@EntityGraph`/`include`/`relations`/`select_related`/`prefetch_related`), or a single `WHERE id IN (...)` batch before the loop, or `@BatchSize`/`batch_size` config | High on user-facing list/detail/checkout paths; Medium on reports; Low if the loop is bounded to < 10 by design (state it) |
| UNBOUNDED | Select-all without paging | Data call has no `Skip/Take`, `Pageable`, `take/skip`, `limit/offset`, `LIMIT`, `[:n]`, cursor; returned from a handler or exported | Paging parameters bound from the request with a max page size, or the table is a small reference set (enums, countries) - state the bound | High when the table grows with business activity (orders, logs, products in a multi-tenant SaaS); Medium for admin-only; Info for reference tables |
| TRACKING | Read query with change tracking | EF: no `AsNoTracking()` / `QueryTrackingBehavior.NoTracking` on a query whose result is only serialised. Hibernate: entities loaded in a transaction and never modified (use DTO projection or `readOnly = true`). Django/Prisma/TypeORM: N/A - flag instead full-entity load when a projection would do | `AsNoTracking()`, `AsNoTrackingWithIdentityResolution()`, context-wide `UseQueryTrackingBehavior(NoTracking)`, `@Transactional(readOnly = true)`, `.Select(dto)` | Medium on large result sets (> 100 rows); Low otherwise |
| INDEX | Filter/sort column with no index | `Where`/`OrderBy`/`filter`/`order_by`/`where`/`orderBy` on a column that `audit-db-schema` lists as unindexed, or a composite filter (`CompanyId, BranchId, X`) whose index does not start with the filter columns | Index present covering the filter's leading columns; or table small and static | Medium (High if the query is the main list page); always cross-reference the DB finding id |
| TXN | Multi-table write without a transaction | Two or more `SaveChanges`/`save`/`create`/`update` on different tables in one business operation with no `BeginTransaction`/`@Transactional`/`$transaction`/`atomic()`; or a transaction started but a later call uses a different context/connection | One unit of work: single `SaveChanges` with all entities attached, `@Transactional` on the service method, `prisma.$transaction([...])`, `with transaction.atomic():` | High when money or stock moves (order + stock + ledger); Medium otherwise |
| INEFFICIENT | Client-side evaluation, over-fetch, Count vs Any | `.ToList()` before `.Where()`; `.AsEnumerable()` mid-query; `.Count() > 0` / `.Count() == 0` / `len(qs) > 0` / `count() > 0`; loading full entity to read one column (`FirstAsync(...).Name`); `SELECT *` via `find()` with no `select`; `.Include` of a collection that is not used; `string.Contains` on a non-indexed column with leading wildcard; Django `.all()` then Python filtering; `exists()` missing | Server-side filters, `Any()`/`exists()`/`count > 0` via `EXISTS`, `Select` projections, `only()`/`values()`, `select: {}` | Medium when on a hot path or large table; Low otherwise |

## Rating notes
- Multiply by traffic: an N+1 with 50 rows on the landing page is worse than 500 rows on a monthly report. Write the estimated queries-per-request into Impact.
- Multi-tenant SaaS: an unbounded list is bounded per tenant only if the tenant filter is applied *before* materialisation - check `Where(CompanyId)` precedes `ToList()`.
- `confidence: likely` when the loop body calls a repository method you could not open, or paging may be applied in a base class you could not resolve.

## Evidence to keep
For each confirmed finding: the query site, the loop or handler around it, the estimated row count (ask the team or infer from entity semantics), and if query logging was available, the actual query count for one request.
